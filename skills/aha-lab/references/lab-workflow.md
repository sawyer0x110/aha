# Lab 编排与检查

## 最小教学单元

默认交付给最终读者。先直接解释主题，给一个可预测的最小案例和具体对照／步骤，再提出理解题并提供有理由的答案；不要交给读者一份作者待办。数值模型可以比较只改变一个主要条件的案例，概念主题不必假装有计算实验。不要用复杂动画遮蔽规则。

| 路由 | 建议案例 | 必须说清 |
| --- | --- | --- |
| 重试 | 两次可重试失败后成功；0 次重试；不可重试错误立即停止 | 首次尝试与重试次数不同；等待是逻辑时间 |
| 复利 | 同一组收益率排列；再加入同一时点现金流 | 无现金流、无逐期舍入时排列不改变最终金额 |
| 证据 | 用已审阅主张解释概念对照或具体步骤，再提供来源查阅 | 概念图不是运行轨迹；案例保留适用条件与未知项 |

模型具体边界、Draft 和命令见 [共享契约](authoring.md)。一个 Pack 只使用一个引擎；比较前核对模型版本与假设一致。

在设计交互之前，按 [代码库研究](research-codebase.md)／[公开内容研究](research-public.md) 完成问题分解、取证、反证与缺口台账；然后按 [受众适配](audience.md) 调整词汇和深度。页面结构不是研究方法，调用次数或控件数量不是理解效果的证据。

按 [解释设计](teaching-design.md) 明确预测／解释／迁移目标、误解与先备知识，再选择具体内容。有来源的状态变化可用 teaching：先显示操作前态并收预测，再揭示实际变化与未变对象、给选择专属反馈，最后归纳规则并做新情境迁移；仅回放记录／来源例子，不执行 Git。没有合适序列时保留概念比较或适配的数值引擎，不伪造中间态。

## 从材料到交互

1. 写出材料真正支持的主张、反证和未解决问题。每条代码断言有版本／文件／符号／行和内容哈希，网页有实际阅读范围与获取时间；首次建包前研究／Draft 须明确审阅。已审阅且事实／证据不变的呈现纠正按 [审阅范围](authoring.md) 执行，不新增纯 UI 审批。
2. 选出与主张有关的案例；数值模式列明输入单位和可调整边界。来源模式用 `brief.explanation.visual` 的 `cards`／`steps` 或有依据的可选 teaching 直接解释关系，配条件与答案；不把读者选中了几份来源当结论。
3. 数值模式独立写出预期结果，再查看程序输出。输出与预期冲突时先检查问题前提、模型规则和输入，不改预期来迎合结果。
4. 把结果解释关联到 Claim 和 Evidence；正文中的固定数字应对应保存案例，不用于描述所有临时参数组合。
5. 对不适配内置模型的材料，向委托人明确采用来源讲解，不声称“完整模拟原系统”。最终读者先看主题解释，来源查阅是次级入口，不是主要学习活动；必要事实条件用自然语言说清。

图示只接受普通字符串，引用已有 Claims，不是可执行 HTML、新模型或观察轨迹。受众标签、来源计数、Claim ID、哈希与生产／审批指令留在 Pack、台账、回执和来源元数据，不放可见教学区域。自然保留简洁来源及必要条件，不能把不确定性一并隐藏。例：天气百分比是否是假设、预报产品的时间窗与阈值；Git 普通 add、按块 add -p、commit -a 的区别，都比协议标语更有教学价值，且只能使用已审阅的对应事实。

用户请求解释一个仓库时，本版可以用获准读取的代码形成来源说明；即使逻辑看似相同，内置重试结果也只能是教学模型，不是该仓库实测。

## 浏览器验收清单

仅在确实具备获准浏览器能力时执行，逐项记录；不能检查的项写明未检查。

- 打开交付的实际 `.html` 文件，而不是开发服务器页面。
- 无需 Pack 相邻目录、Node 或 CDN 才能显示。
- 有效输入确实改变重算结果；非法输入显示错误，不截断成合法值。
- 前后单步、重置和播放回到相同语义状态；调播放速度不改变结果。
- 对照列明输入差异和自然语言适用条件，不把同时改变多个条件说成单变量因果；协议标签留在元数据。
- 来源、限制和未知项可读；证据模式没有伪造模拟或轨迹。
- teaching 先预测后揭示，实际点一次正确与错误选项，检查具体反馈、目标 delta、复制方向与未变对象；前后回放不暗示真的执行 Git。
- 不看研究台账也能读懂解释图示并核对理解题答案；首屏不是来源选择器或审计报告。
- 实际操作讲解选择器，确认主题讲解对应所选内容；再操作次级来源选择器，确认材料查阅没有冒充新的模型计算。
- 可见页面无受众／来源计数／Claim ID／哈希／生产指令；主题步骤没有被“研究 → 建包 → 渲染”替代。
- 下载仅由显式操作发起；实际触发浏览器下载并读取记录，确认选择的案例和笔记保留。CLI 导出只验证文件协议，不能替代浏览器下载验收。
- 中文内容、窄屏、键盘操作与减少动画设置检查后再报告结果。

CLI 的 HTML 检查不等于这份浏览器检查，也不等于真实性审查。

按 [检查—修订闭环](quality-loop.md) 保存代表性 pilot 的预测前／揭示后／错误反馈截图，检查颜色编码、关系、焦点和可读性。先修 Draft／设计／通用实现再重新生成，不手改最终 HTML；同一问题两次局部修补无效就回到设计。读者任务成绩只记实际回答，Agent 视觉审阅不是人类理解测试。生成物、来源记录、版本化截图／日志与迭代默认放忽略的 artifacts 或获准会话目录，只向用户指定的交付目录显式推广一套当前成品，旧输出留可回滚归档。

## 交给 Story

交付**原始 Pack 路径 + exploration 路径**，而非只有 HTML。CLI 导出与页面显式下载使用同一探索协议。

记录允许 1–10 个案例；数值 Story 的 5–8 页模板每次导入 1–4 个，超过 4 个返回 `STORY_CASE_LIMIT` 且不创建 Pack，不静默遗漏；重新选取或分批导出，不截断记录或改哈希。来源模式保留已有 `narrative`（含图示／条件），选择留在新修订与导入回执，不制造面向作者的交接幻灯片。Lab A/B 两案例导出不受影响。

保留用户备注原意，并注明它是主观观察／疑问。只有补足独立依据后，备注中的断言才有资格成为新的主张。

导入后的主 HTML、卡片／PNG 和原生 PPTX 应从实际导入的 Pack 渲染，并核对产物／回执身份。原 Pack 仅用于导入绑定和回溯，不能改回源 Pack 输出再声称已测试新修订。
