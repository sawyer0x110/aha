# 受众适配：改变解释方式，不改变事实

先完成 [代码库研究](research-codebase.md)／[公开内容研究](research-public.md)，再决定词汇、类比、深度与 framing。受众信息改变解释路径，不能改变数字、单位、来源、条件、失败边界或不确定性。

## 默认与背景

- 默认成人初学者、中文、单主题；儿童版的同意、隐私与教学设计不在当前范围。
- 使用用户明确提供的知识与任务；年龄、学历、职业或亲属关系不等于知识水平。不推断“经理不懂技术”或“工程师必懂此领域”。
- 只在影响理解时补问已知概念、实际决策和预期深度；没有信息就在作者的 Brief 中注明假设，使用尊重且简洁的成人表达。`brief.audience` 是内部编写输入，不在成品印上“为谁讲解：成人初学者”。
- 先写一句受证据支持的 takeaway，再选择哪些机制和边界对当前任务必要。不虚构 ROI、工期或收益以迎合受众。
- 按 [解释设计](teaching-design.md) 写“读者将预测什么、解释哪个变化、迁移到哪种新条件”；列可能误解和先备知识，用具体内容例子纠正它。takeaway 是作者假设的归纳，展示时先让读者经历例子再给规则，不先灌定义表。

## 同一事实集的不同入口

| 受众／任务 | 词汇与深度 | framing 与检查 |
| --- | --- | --- |
| 管理者，需要决策 | 先解释必要术语，保留会改变决策的机制；按已知背景提供技术细节 | 决策、影响、成本／风险与权衡；未测量的影响标未知，不编造建议收益 |
| 工程师，需要排障／实现 | 使用准确符号和领域词，但不假设跨领域知识；可逐层展开 | 机制、输入／输出契约、状态、配置、错误／重试／取消及验证办法 |
| 成人初学者，需要建立心智模型 | 一个概念一层，首次出现术语即解释；至多一个有边界的核心类比 | 先具体案例再抽象规则；给一个能检验迁移理解的 check question |

其他受众仍从任务与已知背景出发；不是套职业模板。受众拥有技术背景时尊重它，不为“通俗”删除关键事实。

## 类比不是证据

- 类比映射本次需要的一个关系，写清映射对象与不适用处；不要堆叠多个互相矛盾的故事。
- 不用儿童化或身份刻板的类比，不因年龄假定其兴趣和生活经验。
- `analogy.limitations` 必须说明哪里不成立，例如逻辑等待不是真实排队时间。类比不能给源系统增加保证、因果或参数。
- 用户不需要类比就省略它；机制本身清楚时不强制比喻。

## Draft 中的可选解释层

`brief.explanation` 是可选结构；启用时填写：

| 字段 | 要求 |
| --- | --- |
| `takeaway` | 一句话中心结论，可回到 Claim；不扩大适用范围 |
| `analogy` | 可省略；存在时包含 `text` 与 `limitations` |
| `glossary` | `{term, meaning}` 数组；关键术语准确，不能用词汇简化改变定义 |
| `checkQuestion` | 检验能否应用规则的一个问题；避免仅问“懂了吗” |
| `visual` | 可选 `TeachingVisual`：`layout: "cards" \| "steps"`、标题最多 80 字符、2–4 项 `{label, body}`（分别最多 40／160 字符）及引用现有 Claims 的非空 `claimIds` |
| `conditions` | 可选，最多 6 条自然语言事实条件，每条最多 180 字符；不是生产或审批要求 |
| `answer` | 可选，最多 400 字符的理解题答案；给出判断及理由，让成品无需另一位作者补讲 |

已有无此字段的 Pack 仍有效，`takeaway`／`glossary`／`checkQuestion` 等既有约束不变。Slide 也可有同形状的 `visual` 与 `conditions`。全部文本是普通字符串，不是 HTML／代码执行；解释图示不是新模型、外部证据或观察轨迹。新增事实仍需改主张台账、补证并审阅。

## 最终读者优先

成品默认给最终读者，不给委托人或下一位 Agent 分派工作。先直接解释“是什么／为什么”，用具体概念对照或步骤支撑，最后给理解题及有理由的答案；不是将 Brief、Claim 和审计字段换一套标题。图示画主题关系，不画制作管线；先懂概念再查来源，选择来源不是主要学习活动。

可见图卡、正文、幻灯片、旁白与 Pack `narrative.slides[].notes` 的讲解文字不放受众标签、来源计数、Claim ID、哈希、“原解释包讲解要点”或生产／协议／验收指令；这些信息保留在 Pack、研究台账、回执和来源元数据。保留简洁的来源名称／链接与必要事实条件，不用“来源阅读非因果模拟”替代具体解释。

原生 PPTX 审计备注与内嵌 Pack 有意保留完整来源身份和研究元数据，与上述读者讲解字段不同，不要求清除其审计信息。TTS 使用 Pack 的 `narrative.slides[].notes` 准备旁白，不使用原生 PPTX 审计备注；分享前仍审查备注与内嵌数据。

例如，若已有已审阅主张支持：天气概率讲解明确某个百分比是假设例子，不是实时预报，时间窗和降水阈值依具体产品定义；Git 讲解区分普通 `git add` 保存所选路径当前内容、`git add -p` 按块选择、`git commit -a` 自动暂存已跟踪修改但不包括新未跟踪文件。图示和答案表达这些区别，不暗示页面真的执行 Git 或模拟天气。

交付前人工核对各版本的 Claim／Evidence ID、内容身份、事实、单位、参数、来源和关键限制不变；Claim ID 只用于内部核对。Lab、图片、PPTX、HTML slides、旁白与字幕沿用已批准内容，不在 renderer 中悄悄增删事实。缩短篇幅删次要展开，不删成立条件。

首次构建仍需明确研究／Draft 审阅。用户明确要求纠正已审阅、事实与证据不变的呈现时，该请求授权相应本地修订；按 [审阅范围](authoring.md) 保存旧输出，记录范围和新 Draft 哈希，不为纯排版／UI 再造审批循环。新发现须补证审阅；新旁白外发须另批完整文本、provider、voice、rate、时间安排及当前 `planHash`，不是呈现授权的附赠权限。

## 人工语义验收

依 [检查—修订闭环](quality-loop.md) 请实际读者在没有制作说明、未见答案时预测结果、解释变化及不变量，再解不同情境的迁移题。记录实际回答、提示使用和依据：0＝错误或无理由，1＝结果对但机制／条件不全，2＝结果、理由和条件正确。反馈后改用新情境复核，不重复旧题制造进步；未测写未测，不编造人类反馈，不宣称小样本证明普遍学习效果。

成品截图／颜色／关系／可读性检查和学习回答是两种证据。独立 Agent 视觉审阅只是启发式，不是人类理解测试，也不要求宿主支持委派。相同事实要按 [每种媒介设计](formats.md) 重组，不只是修改词汇、字号或页数。

仓库中的 benchmark prompt fixtures 只做结构检查。宿主是否正确触发 Skill、真的取证、适配是否准确、有没有刻板印象，均需在真实宿主中人工语义评估；静态字符串命中不证明这些行为。
