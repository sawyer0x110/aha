# 检查—修订闭环：成品可读不等于读者已懂

此流程检查 [解释设计](teaching-design.md) 在实际媒介上是否成立，不增加纯排版审批，也不把结构测试当语义证明。三个 Skill 可独立使用；只有研究交付时检查主张、依据、反证和缺口，不强制生成截图或媒体。

## 1. 先制作代表性 pilot

选最能暴露设计风险的一幕，不挑最空的封面：一次状态改变、一个易混关系或最密的机制页。先从规范 Draft 经 Skill CLI 构建新 Pack，渲染用户所选格式的小样／预览，保存实际文件的代表性截图。Lab 保存预测前、揭示后及一次错误反馈；PNG 看完整图片；slides／PPTX 看机制页与迁移页。视频先检查分镜静帧，再在获得音频授权时做真正短片；静帧不算视频听审。

记录输入／Pack 身份、实际命令、产物与截图位置、观察到的缺陷和未执行项。没有浏览器／演示程序等能力时标明阻塞，不拿 DOM、OOXML、文字提取或另一个格式的成功代替实际视觉检查。

PPT pilot 还须连看实际相邻页：状态叙述与图、条件 outcome、transfer 问题页及下一张 answer 页；单页正确不能证明前后连续性。记录失败画面，改通用设计／实现后重新生成并复查同一组页。

## 2. 两条检查线，分别给证据

### A. 成品检查（artifact）

| 检查 | 必须在实际产物中回答 |
| --- | --- |
| 事实与关系 | 具体操作是否匹配前后内容？目标变化 delta 是否可见？未变对象能否认出？复制箭头方向／端点／内容一致吗？必要条件和来源还在吗？ |
| 时态与状态 | 逐句核对“执行前／接下来”对应 before、“已执行／现在”对应 after；hook 的 statePhase 与叙事一致吗？outcome 是否明确“若此时执行”的 rule-application，而非声称已观察到执行？ |
| 跨页连续性与内容原样 | 同一实体位置／顺序是否稳定？同一种箭头是否始终表达同一关系？把实际代码／content 与保留内容逐字核对，高亮是否仅用样式／独立标注，没有添加 `+`、`>`、星号等字符或删除原有字符？ |
| 颜色编码 | 同一对象／变化含义跨页是否一致？颜色是否表达了错误因果或把未变对象也画成变化？用位置、文字或边框补充颜色，不能只能辨色才能解题 |
| 焦点与可读性 | 第一眼看哪里？标题是否提出一个可回答的问题／结论？真实观看尺寸下中文、内容差异、箭头与字幕可读吗？是否遮挡、溢出、拥挤，或留白多到关系断开？ |
| 媒介适配 | PNG 是否只有一个视觉论证？Lab 是否先预测再揭示并给具体反馈？slides／PPTX 是否按场景换构图和层级？视频的旁白与画面是否分工而非全文朗读卡片？ |
| 阅读路径 | 不看制作说明能否找到问题、案例、差异、规则和迁移题？可见内容是否混入受众标签、Claim ID、哈希或审批文字？来源是否为次级入口？ |
| 迁移与答案揭示 | 实际 PPT 中 transfer 和同一 checkId 的 answer 是否为相邻两页，下一页才显示正确答案？answer 是否解释正确理由及每个错误选项的理由，而非空 notes／“答案见备注”占位？ |

逐项记录“满足／阻塞／未检查”和具体画面证据，不给没有依据的总信心分数。错误关系、差异不可见、关键条件缺失、答案提前泄露导致任务无效、遮挡不可读、所需交互失效或选定格式未生成都是阻塞项。

叙事时态与状态不符、实体跨页换位造成误读、箭头语义漂移、为高亮而篡改实际代码字符、把条件结果伪称观察执行，以及迁移题未实际分出答案页或缺少错项理由，同样是阻塞项；不能因结构测试通过而豁免。

### B. 学习任务检查（learner）

准备答案判据后，请实际读者在不看答案时：①预测下一步；②解释变化及不变量；③完成不同情境的迁移。保存实际回答（尊重隐私）、是否看过提示／答案和给分依据。每项可用 **0＝错误或无理由，1＝结果对但机制／条件不完整，2＝结果、理由和必要条件正确**；分数必须来自观察到的回答，不是字段齐全或作者猜测。错题反馈后用另一道新情境复核，不重复原题制造进步。

没有实际读者就写“学习任务未测”，不得编造人类反馈、提升比例或保证人人理解。自行解答可核对题目，但不是读者样本。可用的独立 Agent 视觉审阅是启发式检查，不是人类理解测试；不要求宿主具备子 Agent，也不在禁止委派时创建它。独立审阅者先只看目标任务和实际产物，不读作者自评；区分它的推断与真实学习回答。

## 3. 按缺陷层级修订，再重新生成

1. 先定位原因：事实缺口回到研究；误解／例子／顺序／迁移题无效回到解释设计；统一卡片、颜色／箭头／密度问题回到媒介设计；重复发生的布局或交互问题修通用 renderer／runtime（须在授权代码范围内）。
2. 修规范 Draft、Skill／共享参考或通用实现，再经相同 Skill CLI 新路径构建／渲染。**不手改最终 HTML／PPTX**，不对单一成品打补丁掩盖上游错误；修后检查受影响的其他格式与旧能力。
3. 对照新旧实际截图，逐条复查原缺陷，并检查修订是否损坏内容、可读性或交互。记录哪些关闭、哪些仍阻塞，不能只看最新图片“感觉更好”。
4. **同一问题经过两次局部修补仍存在，就返回设计层**重选例子、关系或构图，不继续换字号／颜色碰运气。没有任意硬性全局通过轮数；继续到所选交付的阻塞项解决，或具体工具／授权／证据／预算限制使工作无法继续。此时如实报告真实阻塞和下一最小动作，不无限保证“下一轮一定好”。
5. 结论分开写：结构／引用检查、成品视觉／交互检查、真实读者任务成绩、未执行检查。Agent 审阅或截图通过不能被改写为人类理解验收通过；不凭一张好封面批准整个输出集。

## 4. 发布与回滚，不堆积交付版本

- 生成迭代、实时截图、视频静帧和日志放在项目中被忽略的 `artifacts` 工作目录或获准的会话目录；版本号用于工作／归档路径，不是在公开示例中长期堆历史。
- 生成物、批准输入、必要证据、Pack、探索记录与必要回执默认留在忽略的 `artifacts` 或获准会话工作目录，不要求创建仓库案例目录。用户指定交付目录时，只推广一套当前成品；除非用户明确要求删除，不丢弃该交付的必要追溯依据。
- 阻塞项关闭后显式 promotion：核对待推广输出与所选 Pack／回执身份，列出替换目标；归档上一有效集合及恢复办法，再更新当前成品集合和相关指引。不自动宣布或偷偷推广未经检查的输出。
- 保留旧输出意味着保留可回滚归档／工作修订，不意味着交付目录永远追加旧版。创建命令仍写新路径；不修改封存 Pack，不静默覆盖用户文件，不删除唯一有效旧文件来绕过碰撞保护。发布替换须在用户已授权的范围内。
