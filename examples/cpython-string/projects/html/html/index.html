From observation to mechanism

Why one code point can widen a CPython string

In this compact CPython example, one storage width applies to every code-point slot in the result. Adding U+1F600 requires four-byte slots, including the unchanged ASCII prefix. UTF-8 is a different representation.

Compare the new str with its encoded bytes

CPython 3.11.15, compact-string example. Recorded sizes were supplied, not rerun; slot diagrams are not to scale.

One width for all code-point slots

ASCII needs one-byte slots. U+00E9 still fits in the one-byte class; U+4E2D needs two; U+1F600 needs four. The representation range, not an emoji category, determines the width.

Allocate a new result; do not mutate the original

The pinned PyUnicode_Concat path combines operand lengths and representation ranges, allocates with PyUnicode_New, then copies both operands. This source trace does not prove the exact supplied expression dynamically called that function.

Object size includes more than character slots

A supplied CPython 3.11.15 observation reports 100,049 bytes for 100,000 ASCII code points and 400,080 bytes after adding U+1F600. Headers, the terminator and applicable caches affect object size. These are inherited observations, not new measurements.

UTF-8 keeps the ASCII prefix compact

The UTF-8 payload grows from 100,000 to 100,004 bytes. Each ASCII code point still takes one byte; U+1F600 contributes four. Encoded payload length is neither str object size nor total process memory.

Not every non-ASCII addition causes this jump

A result already using four-byte slots does not undergo the same widening. Small strings have different overhead ratios. These totals describe one CPython build and object state, not every Python implementation or every emoji sequence.

从现象到机制

一个码点为什么会让 CPython 字符串变宽？

在这个紧凑 CPython 字符串示例中，新结果的所有码点槽使用同一存储宽度。加入 U+1F600 后，连原有 ASCII 前缀也使用四字节槽；UTF-8 则是另一种表示方式。

比较新 str 与它编码后的字节

CPython 3.11.15 紧凑字符串示例；大小来自既有记录，未重新测量；槽位示意不按实际数量绘制。

一个结果，统一的码点槽宽度

ASCII 可用一字节槽；U+00E9 仍属于一字节类别，U+4E2D 需要两字节，U+1F600 需要四字节。决定宽度的是表示范围，不是 emoji 分类。

分配新结果，不修改原字符串

固定版本的 PyUnicode_Concat 合并操作数长度与表示范围，调用 PyUnicode_New 分配结果，再复制两侧内容。这条源码路径不证明给定表达式运行时必然调用了该函数。

对象大小不只有字符槽

已有 CPython 3.11.15 观察记录：十万个 ASCII 码点的 str 为 100,049 字节，加入 U+1F600 后为 400,080 字节。头部、终止符及适用的缓存都会影响对象大小；这些是继承记录，不是新实测。

UTF-8 中的 ASCII 前缀并不变宽

UTF-8 载荷从 100,000 增至 100,004 字节。每个 ASCII 码点仍占一字节，U+1F600 增加四字节。编码载荷长度既不是 str 对象大小，也不是进程总内存。

不是每个非 ASCII 字符都会导致这种增长

已经使用四字节槽的结果，不会再次经历同样的扩宽；短字符串的额外开销比例也不同。这里的总数属于特定 CPython 构建与对象状态，不适用于所有 Python 实现或 emoji 序列。
