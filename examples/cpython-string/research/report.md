# Why one grinning face widens a CPython string

## Direct answer
For the ordinary compact strings in this example, CPython chooses one character-storage width for the entire resulting str. ASCII fits in one byte per code point. U+1F600 exceeds U+FFFF, so the new concatenated string uses four bytes for every code point, including its unchanged ASCII prefix. UTF-8 is a separate variable-length encoding: the existing ASCII bytes stay one byte each, and this added code point contributes four bytes. These are different representations, not a fourfold increase in file size or total process memory.

## Mechanism and pinned path
PEP 393, Abstract, Rationale, Specification and String Creation, describes 1/2/4-byte representations selected by the largest code point and an ASCII-specific compact header. It is a design source dating to 2010, targeting Python 3.3, not evidence that every historical enum detail remains identical in 3.11.

The python/cpython tag v3.11.15 resolves through annotated tag 2323bfc729b041c43b1e5e4c5f18c548fc345323 to commit 2340a037f7450e70fccfe411e6531afb4d57a312 (tagger date 2026-03-03). At that commit, Objects/unicodeobject.c::PyUnicode_Concat handles type/readiness checks, empty operands and length overflow before taking the greater representation range of its operands, allocating PyUnicode_New(new_len, maxchar), and copying both operands into the result. Include/cpython/unicodeobject.h::PyUnicode_MAX_CHAR_VALUE was also inspected: it returns a kind-dependent upper bound, not an exact maximum scanned on every concat. Thus the accurate implementation description is that concat combines existing representation ranges; it does not rescan every character to discover the maximum. PyUnicode_New chooses one-byte storage below 256 (with an ASCII-specific header below 128), two-byte storage below 65536, and four-byte storage otherwise. It allocates the header plus (length + 1) times the chosen width and writes a terminator. This establishes why a new result containing U+1F600 widens all stored code-point slots. The visual expansion is a diagram of the new representation, not an in-place mutation of the original immutable str. The entire interpreter opcode/optimized append path and copy helper body were not traced, and this research does not claim that the parent's exact expression dynamically called PyUnicode_Concat.

## Supplied actual observation, not a new experiment
The parent reports an existing local CPython 3.11.15 observation using sys.getsizeof and encoded UTF-8 length:

| Input | Code-point length | str object size, bytes | UTF-8 payload length, bytes |
| --- | ---: | ---: | ---: |
| 'a' repeated 100,000 times | 100000 | 100049 | 100000 |
| baseline plus U+00E9 | 100001 | 100074 | 100002 |
| baseline plus U+4E2D | 100001 | 200076 | 100003 |
| baseline plus U+1F600 | 100001 | 400080 | 100004 |

The measurement was supplied as an actual parent observation, not executed or independently reproduced by this author. Its execution timestamp, complete command transcript and build configuration were not supplied. Do not invent them. The exact totals belong to that local build and object state. Python's sys.getsizeof documentation says it counts memory directly attributed to an object. The pinned unicode_sizeof_impl counts the compact header, character buffer and terminator, and separately allocated compatibility caches when present. Header differences explain why totals are only nearly fourfold, not exactly fourfold. In this supplied case, 100049 bytes becomes 400080 bytes; the UTF-8 payload grows by only four bytes. The encoded payload length is not sys.getsizeof of the bytes object and is not a measurement of a written file.

## Counterexamples and alternative explanations
U+00E9 contradicts the tempting claim that any non-ASCII character forces four-byte slots: it remains in the one-byte class, albeit with a larger non-ASCII header. U+4E2D demonstrates the intermediate two-byte class. The rule is a code-point range rule, not an emoji-detection rule; no claim is made about every emoji, multi-code-point emoji sequences, or user-perceived character counts. A string already in the four-byte class would not have the same multiplicative jump. Exact header/cache overhead varies by build and object history, and small strings need not show an approximately fourfold ratio. PEP 393 and implementation source share an implementation lineage, so they are design/implementation corroboration, not two independent empirical experiments. The supplied measurement is the separate observational evidence.

## UTF-8 comparison
Python 3.11 Unicode HOWTO, Encodings, describes ASCII as one byte and other code points as sequences of two, three or four bytes. Converting to Bytes distinguishes str.encode from internal Unicode storage. The supplied U+1F600 observation establishes the specific four-byte increment here. Its prefix remains ASCII under UTF-8; no uniform four-byte width is imposed on that encoded prefix.
