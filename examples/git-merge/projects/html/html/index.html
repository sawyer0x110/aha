不能保证 mode=off

结论：不接受原方案的保证与发布门槛。已撤销的 mode=on 可能作为对侧的非冲突修改进入合并；-Xours 不会阻止它。应把“保持 off、保留所需更新”变成结果验收条件，而不是策略选项的承诺。

逐项审查：哪些假设不成立？

“先在本分支 revert 普通提交，再以默认 ort 策略合并对侧并加 -Xours。这样能保证已撤销的 mode=on 不会回来，同时保留对侧其它更新。合并没有冲突就可以发布。”
① 操作成立，保护假设不成立

先 revert 普通提交

普通 revert 通常通过新提交反转修改，但保留原有历史；它不是“永远禁止 on”的规则。若撤销后相关文件与基点相同，本侧对该文件的净变化就是零。

建议：可用它表达当前撤销意图，不把它当作后续合并的保护锁。下例的撤销已提交；--no-commit 是不立即提交的例外。[1]

② 保证被反例否定

ort 加 -Xours

封存手册中，ort 是合并单个分支的默认策略。-Xours 只在冲突区域偏向本侧，对侧非冲突修改仍进入；其中既可能有想保留的更新，也可能有不想恢复的 on。

建议：按实际结果检查所需路径，不把该选项作为通用过滤器。也不要换成 -s ours：它保留本侧整棵树、忽略对侧内容，反而违背保留对侧更新的目标。[2]

③ 发布门槛不足

没有冲突就发布

文本能自动合并，不等于业务逻辑正确。下例就能在不需要冲突裁决的路径上选入 on；“没报冲突”无法证明撤销意图仍被满足。

建议：发布前明确核对配置结果与其它所需更新，并做相关项目测试和代码审查；本次未验证目标仓库的发布就绪状态。[3]

关键不是撤销记录，而是三个文件状态

Git 先沿历史找最佳共同祖先作为基点，再以基点与双方当前树做内容合并；不是逐个重放提交，也不是完全不看历史。多个最佳共同祖先时，ort 会先合成祖先树。[4]

最小修订：验收内容，不押注选项

  1. 先确定实际比较对象。记录目标 Git 版本、策略、选项与双方提交；检查最佳共同祖先及相关路径的三侧内容。仅有方案描述，尚不能判断目标仓库的具体结果。
  2. 把目标写成明确的结果要求。如果发布要求是 mode=off，就逐项核对合并结果中的该值和需保留的对侧更新；若不符，先明确修正所需内容，再重新审查，而不是换一个 “ours” 开关求保证。
  3. 再判断能否发布。完成相关测试和代码审查，尤其确认保持 off 时其它更新仍满足预期。无冲突只是合并层面的信息，不替代这些验收。
