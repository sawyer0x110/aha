Git / the missing third state

Why can a Git merge bring back a reverted change?

A revert changes your branch’s content. It does not tell a future three-way merge to ban that content on every other branch.

To explain the result, compare the common base with both current versions—not just the last commit message.

The history tells you where to compare

A branch tip is the commit a branch currently points to. The merge base is a best common ancestor of both tips. Git uses history to find that base; the content merge then compares the base tree with the two current trees.

Change the base. Change the answer.

Read these as three versions of one ordinary file, feature.txt. The model assumes matching file modes, no renames and no custom merge driver. The controls switch between reasoned cases; they do not run Git.

Ours nowmode=offSame as B: no net change
Theirs nowmode=onChanged from B
Result: mode=on

Ours equals the base. The other branch still carries the change, so the ordinary-file three-way selection takes its on version. The revert was real; it simply left no net difference here.

The symmetric file-selection rules are visible in merge-ort.c. If both sides differ, content merging may need conflict resolution—not every difference is a conflict.

The returned change does not erase everything else

The comparison is not “choose one entire branch.” Other paths can have a different unchanged side, so an ordinary merge can retain independent work from both branches.

Three distinctions that prevent the wrong fix

Ordinary revert is not reverting a merge

An ordinary revert usually records a new inverse-change commit and keeps the original history. With --no-commit, it does not immediately commit. A merge revert uses -m to select a mainline parent and reverses the change relative to that parent. The merge ancestry remains, so a later merge does not simply replay all the previously merged work. Inspect the later history before choosing a repair.

Git revert manual
Reset changes a different part of the model

The commit form of reset moves HEAD; its mode determines what happens to the index and working tree. A path reset only updates the index. Moving a branch can change which ancestors a later merge shares. Matching visible files do not imply matching history. --hard can overwrite data; this is a distinction, not an instruction to run it.

Git reset manual
A strategy is not a conflict preference

ort is the current default for merging one branch. -s ours retains our entire tree and ignores the other branches’ content. -Xours only favors our conflicting hunks; their nonconflicting changes still enter. Neither is a universal safe fix. In current Git, recursive is an alias for ort, a change made in 2.50.

Git / 别漏掉第三个状态

为什么 Git 合并会带回已撤销的修改？

撤销改变了本分支的内容，却不是要求未来的三方合并永远禁止其它分支带入这项内容。

要解释结果，应该拿共同基点分别比较两侧当前版本，而不是只看最后一条提交消息。

历史决定应该从哪里开始比较

分支的最新提交，就是分支当前指向的提交。合并基点是双方的最佳共同祖先。Git 先通过历史确定基点，再比较基点树和两侧当前树的内容。

这是说明性模型，不是已执行实验。连线从左到右表示父子提交关系。Git 2.55 合并基点定义。

换一个基点，答案就可能反过来

下面是普通文件 feature.txt 的三个版本。假定文件模式相同、没有重命名或自定义合并驱动。按钮切换的是基于资料推导的案例，不会运行 Git。

合并基点 Bmode=off共同的起始内容
本侧当前mode=off与 B 相同：净变化为零
对侧当前mode=on相对 B 有变化
结果：mode=on

本侧与基点相同，对侧仍保留修改，所以普通文件的三方选择会采用对侧的 on。撤销确实发生过，只是在这里没有留下相对基点的净变化。

merge-ort.c 的对称选择分支解释了前两种结果。两侧都有变化时可能需要解决冲突，但不是所有不同修改都会冲突。

带回一项修改，不等于丢掉其它工作

普通合并不是“从两条分支中整条选一条”。其它路径上，与基点相同的可能是另一侧，因此两边的独立工作可以同时保留。

先分清三件事，别急着“修复”

撤销普通提交，不等于撤销合并提交

普通 revert 通常新建反向修改的提交，原历史仍保留；使用 --no-commit 时不立即提交。撤销合并提交需要 -m 选择主线父提交，反转相对该父提交的变化。合并的祖先关系仍在，所以后续合并不会简单地重放先前所有工作。应先审查后来的历史，再决定怎样修复。

Git revert 手册
Reset 改变的是另一部分模型

提交形式的 reset 移动 HEAD，模式决定索引和工作区如何变化；路径形式只更新索引。移动分支指针可能改变未来合并的共同祖先。文件看起来相同，不代表历史相同。--hard 可能覆盖数据；这里是在解释区别，不是在建议执行它。

Git reset 手册
合并策略不是冲突偏好选项

ort 是当前合并单条分支的默认策略。-s ours 保留本侧整棵树，忽略其它分支内容；-Xours 只在冲突区域偏向本侧，对侧不冲突的修改仍会进入。两者都不是通用的安全修复。在当前 Git 中，recursive 已是 ort 的同义名，这一变化始于 2.50。
