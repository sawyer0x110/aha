GIT MERGE · FROM HISTORY TO FILE CONTENT

Why can Git merge bring back a change we reverted?

In a configuration file, our branch changed timeout from 30 to 60, then reverted that change, restoring 30. Another branch kept the change from 30 to 60. When we merged that branch, the recorded result was timeout = 60.

Base30shared baseline
Ours30after reverting the change
Theirs60change still present
Result60clean text merge

Git did not count commits as votes. For this file, ours ends up identical to the base, so there is no net change on our side to combine. Theirs differs from the base, so its changed content is selected. A revert changes our branch's content; it does not tell a later merge to reject the same change from another branch.

This is an actual recorded revert case, not a simulated answer. The Git strategy manual explains the same behavior. Evidence and methods

History finds the baseline.
Snapshots reveal the changes.

A commit records a version of the project. A branch names its latest commit; that commit's snapshot tells us what the files contain now. In the ordinary two-branch merge here, ours means the branch we are on, and theirs means the branch we are bringing in. HEAD identifies our current checkout.

Base · the shared baseline
A best common ancestor in the commit graph: a commit both branches descend from. It is selected by ancestry, not by the newest timestamp.
Ours · our latest snapshot
Compare this file with the base file. What content is different after all our edits and reverts?
Theirs · their latest snapshot
Compare their file with the same base file. Git then tries to combine these two sets of base-relative changes.

The useful question is not “Who committed last?”
It is “What changed on each side since the shared version, and can those changes be combined?” History still matters for finding the base. The content merge is not a chronological replay of every commit.

These examples have one base. More complex ancestry can yield several best bases; ort can combine them into a reference tree. Nor must the three file contents be different: in the revert case, base and ours are byte-for-byte equal.

Recorded files and command · Git's description of unresolved merges and index stages

First check whether the branches actually diverged.

The first two recorded cases created a new commit with two parents because they combined divergent histories. But not every git merge needs a new commit—or a content reconciliation like the one above.

Fast-forward: ours is already an ancestor of theirs.
Imagine our branch still points to an earlier commit on the other branch's existing path. Git can simply move our branch pointer forward to their latest commit. There is no separate line of work to combine.

This uses an existing commit, rather than manufacturing a merge commit. Options such as --no-ff can request a different result. This contrast comes from the manual's fast-forward description; it was not a fourth recorded experiment.

A clean text merge does not prove the program works.

The merge machinery compares file content and change regions. It does not run the application to check whether names, calls and behavior still agree.

No conflict, but a broken call

One branch renames a function in its definition file. The other branch adds a call to that function's old name in another file. The text changes can combine without overlap, yet the new call can point to a name that no longer exists. Tests or review must catch that mismatch.

A conflict, but no behavior dispute

Two branches can rewrite the same comment differently. Git may need a person to choose the wording even though neither edit changes executable behavior. A text conflict alone does not prove the two features are incompatible.

These are reasoned illustrations from the dossier, not executed application tests. The strategy manual also warns about mismerges.

Read the base, read both current versions, then check the combined behavior. That is more useful than counting commits—and remains necessary even when Git reports success.

GIT MERGE · 从提交历史到文件内容

为什么 Git 合并
会带回已撤销的修改？

在一个配置文件中，我们把 timeout 从 30 改成 60，随后撤销这次修改，恢复为 30。另一个分支仍保留着从 30 改成 60 的修改。合并那个分支后，实际记录中的结果却是 timeout = 60。

基线 Base30双方共同的起点
当前分支 Ours30撤销这次修改之后
待合入分支 Theirs60仍然保留修改
合并结果60文本合并成功

Git 并不把提交次数当成票数。对这个文件来说，我们的最终内容与基线完全一样，因此没有留下净变化；对方相对基线有变化，Git 便采用了对方的内容。撤销操作改变的是我们分支上的文件，并没有给以后从其他分支合入的同一修改加上一条“禁止进入”的规则。

这来自真实的撤销实验记录，不是页面模拟出的答案。Git 合并策略手册也解释了这种现象。查看证据与方法

用历史找到基线，
用快照比较变化。

一次提交记录项目的一个版本，分支指向它的最新提交。这个提交中的快照，告诉我们文件现在是什么样。这里讨论普通的双分支合并：ours 是当前所在分支，theirs 是准备合入的分支；HEAD 标识当前检出的提交位置。

Base · 比较用的共同基线
它是提交图中的一个最佳共同祖先，双方都从它发展而来。Git 按祖先关系寻找它，不是挑时间戳最新的提交。
Ours · 当前分支的最新快照
把这个文件与基线文件比较：经历修改和撤销之后，到底留下了哪些内容差异？
Theirs · 待合入分支的最新快照
也与同一份基线比较。接着，Git 尝试把两边相对基线的变化组合起来。

关键不是“谁最后提交”。
而是“两边从共同版本出发，各自留下了什么变化？这些变化能否合在一起？”历史仍然决定基线的选择，但文件内容的合并不是按时间顺序重放每一条提交。

这里的每个例子都只有一个基线。更复杂的历史可能有多个最佳共同祖先，ort 可以先把它们合成参考树。三份文件也不一定内容各异：撤销案例中的 base 和 ours 完全相同。

不过，先看看历史是否真的分了叉。

前两条实验记录合并了分叉的历史，因此生成了各有两个父提交的新提交。但并非每次 git merge 都要创建合并提交，也不是每次都需要像上面那样合并文件内容。

快进（fast-forward）：当前提交本来就在对方的历史路径上。
如果当前分支只是停留在对方那条历史路径的较早位置，Git 可以直接把当前分支指针推进到对方的最新提交。没有另一条分叉出来的工作需要合并。

这时使用的是已有提交，而不是新造一个合并提交。--no-ff 等选项可以要求不同的结果。这个对照来自手册对快进的说明，不是第四条实测记录。

文本合并成功，不等于程序能正常工作。

合并机制比较的是文件内容和修改区域，并不会运行应用，验证函数名、调用和行为是否仍然相互匹配。

没有冲突，调用却坏了

一个分支在定义文件里重命名了某个函数；另一个分支在其他文件里新增了一处调用，用的还是这个函数的旧名字。两处文本修改可以互不重叠，合并后新调用却可能指向一个已经不存在的名字。这种问题需要测试或代码审查发现。

发生冲突，也未必有行为矛盾

两边把同一条注释改成不同措辞，Git 可能需要人来选定文字，但两项修改都不改变可执行行为。因此，仅凭文本冲突，不能断定两个功能无法共存。

这两个例子是研究材料中的推理说明，不是已经运行过的应用测试。合并策略手册也提醒了错误合并的风险。

看基线，看两边现在的内容，再检查组合后的行为。这比数提交次数更有用；即使 Git 报告成功，最后一步也不能省略。
