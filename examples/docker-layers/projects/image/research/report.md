# Docker image layers: hidden is not erased

## Direct answer
For an ordinary unsquashed image diff, the first RUN records a newly created file in an immutable image layer. A later RUN records deletion in a newer layer; a whiteout makes the lower path absent in the merged filesystem view, without rewriting the earlier layer blob. Creating and deleting a NEW file inside one RUN instead leaves that path absent at the before/after diff boundary, so its temporary payload is not added to that resulting diff. This does not imply that every other change or metadata entry disappears.

## Evidence and reasoning bridge
Docker's [Understanding the image layers](https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/) says layers are immutable filesystem changes and describes a unified view plus a separate writable directory for a running container. The diagram concerns image changesets, not that container writable layer.

OCI [layer.md at the pinned commit](https://github.com/opencontainers/image-spec/blob/af26a05fba5ee648512f4ea3c9fda1fcc1b6d6dc/layer.md#whiteouts), lines 151–253 within the read range 1–260, specifies that changes to the comparison snapshot do not affect its source; the changeset contains added/modified content and whiteouts for removals. A whiteout is a special empty entry named .wh. plus the deleted basename. It applies only to lower layers and is itself hidden after application. Thus a visible whiteout in our CUTAWAY is an inspection of the layer representation, never an ordinary file shown in the merged view. 'Empty' in the diagram means the example path is absent, not that the image has no other filesystem entries.

In daemon/graphdriver/fsdiff.go lines 48–104, NaiveDiffDriver.Diff gets the layer and parent, calls archive.ChangesDirs(layerFs, parentFs), then archive.ExportChanges. An empty parent takes a full-tar branch. Errors stop the path. In pkg/archive/changes.go lines 248–359, FileInfo.addChanges walks the new children and remaining old children: newly present paths produce additions; leftover old paths produce deletions. A temporary new path absent from both endpoint trees has no payload to export. Directory metadata may still differ. Lines 392–445 show ExportChanges: a ChangeDelete writes a zero-size tar header using WhiteoutPrefix plus the basename; other changes call addTarFile. This code reads the parent and writes a new archive; it is not an erasure pass over old layer blobs.

In pkg/archive/archive.go lines 1078–1182, Unpack chooses getWhiteoutConverter(options.WhiteoutFormat), calls ConvertRead, propagates conversion errors, and skips ordinary file creation when conversion returns false. In pkg/archive/archive_linux.go lines 15–106, OverlayWhiteoutFormat selects overlayWhiteoutConverter. ConvertWrite translates a zero-device character whiteout into a regular zero-size whiteout tar entry; ConvertRead recognizes the prefix, creates the original-name character device via unix.Mknod, sets ownership and returns false so the marker is not written as an ordinary file. The opaque-directory branch sets an xattr instead. These are concrete serialization/application paths, not a claim about the user's uninspected local storage driver. We did not trace every link between the classic builder commit and this fallback graphdriver or every optimized snapshotter.

Docker [build best practices](https://docs.docker.com/build/building/best-practices/#run), the RUN apt-get subsection, corroborates the final-diff consequence with cleanup in the same RUN: apt list cache is not stored in a layer. Its cache-busting discussion concerns a different problem and is not used as evidence that earlier payloads are reclaimed.

## Example, counterexample and units
The user-specified 100 MB is an assumed uncompressed new regular-file payload (100,000,000 bytes), not a build observation. It excludes base layers, archive/config overhead and compression; compressed image bytes, transfer bytes, cache usage and shared physical storage must not be equated to this number. The image need not be exactly 100 MB larger on disk or over the network. No payload file was created.

Counterexample: removing a file already present in a base layer, even within one RUN, cannot retroactively reclaim that lower blob's bytes. The final-diff comparison has an old path to delete, unlike the absent-before/absent-after new temporary file. Squashing, multistage selection, special mounts, sparse-file behavior, cache pruning, deduplication, image flattening and environment-specific optimizations are outside this pilot. The animation demonstrates the specified ordinary Linux image-layer behavior; it is not a measurement of this Windows host or its builder.
